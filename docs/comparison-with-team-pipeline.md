# 自分（Nanjo）とチーム（`feat/common-infra` → PR#13）の比較

チームの正式パイプライン化に向けて、何が同じで何が違うかを整理する。コードは両方とも実際に読んで確認済み（チーム側は`feat/tune-base-params`ブランチ＝PR#2→#3→#13を積んだ最新状態）。

## 結論（先に）

**検証方法の設計思想は完全に同じ**（独立に同じ結論に辿り着いた）。違うのは主に、①高カード性カテゴリの扱い方、②特徴量の作り込みの深さ、③後処理の有無。お互いに相手の持っていないものを持っているので、**合流すれば単純に足し算で良くなる可能性が高い**。

## 同じもの

| 項目 | 内容 |
|---|---|
| 検証方法 | walk-forward時系列CV、3fold、検証期間3四半期（テスト期間と同じ長さ）。fold境界もほぼ一致 |
| ランダムKFold不使用 | 理由（未来の情報が過去の予測に混ざる）も同じ結論 |
| 目的変数 | `log1p(価格)`で学習、`expm1`で円に戻す |
| ベース特徴量 | 経過四半期・築年数・駅距離・面積の数値化ロジックがほぼ同一（駅距離の範囲表記→中央値換算の値も4区分とも実質一致） |
| モデル | LightGBM、`learning_rate=0.05`、`seed`固定 |
| 駅乗降客数データ | 両者が独立に試し、「効果なし」という同じ結論 |
| ルール遵守 | テスト期間データの外部参照禁止など、規約の理解は同一 |

## 違うもの

| 項目 | 自分（Nanjo） | チーム（PR#13時点） |
|---|---|---|
| コード構成 | `my_project/`にフラットなスクリプト群 | `src/data`/`src/features`/`src/model`に工程分割、ruff・型ヒント・Googleスタイルdocstring徹底 |
| 高カード性カテゴリ（地区名1,210種・駅630種）の扱い | OOF target encoding（5-fold、smoothing=20）を**追加の数値特徴量**として付与。生カテゴリもそのままLightGBMに渡す | LightGBM**ネイティブ**のカテゴリ分岐パラメータ（`cat_smooth`）を**10→50**に調整。target encodingはまだ無い（導入予定） |
| 間取り・建物の構造・用途 | 部屋数+LDKSフラグ、RC/SRC等のマルチホットフラグに**分解** | **生カテゴリのまま**（分解していない） |
| 戦前物件の建築年 | `built_year`はNaN、`is_prewar`フラグで情報を残す | `1945`という代表値を直接代入 |
| ハイパーパラメータ | `num_leaves=63`, `feature_fraction=0.8`, `bagging_fraction=0.8`（やや強めの正則化）。`cat_smooth`は未調整（デフォルト10のまま） | `cat_smooth=50`以外はLightGBMデフォルト（`num_leaves=31`, `feature_fraction=1.0`, `bagging_fraction=1.0`）。**こちらは正則化が弱い代わりにcat_smoothで高カード性カテゴリの過学習を抑える設計** |
| 後処理 | **isotonic価格較正**あり（CV 0.20462→0.20118） | 後処理フック(`postprocess.py`)はあるが中身は未実装（今は何もしない） |
| 木の本数の上限 | `num_boost_round=2000`固定（実際のbest_iterationは1900前後で上限に近い。**要確認: 上限で頭打ちになっていないか**） | `num_boost_round=10000`（CVはearly stopping、本番は3foldのbest_iteration平均を使用） |
| train/testの結合方法 | train由来のカテゴリ一覧をtestに適用（別々に処理） | train+testを先に結合してから全列変換（is_trainフラグで後から分離） |

## 自分側にあって、チーム側にまだ無いもの

- isotonic価格較正（後処理） — ミーティング資料でも「効果が大きい」と評価済み
- 間取り・構造・用途の分解
- target encoding（ただしfold-safeな仕組みがチーム側にまだ無いので、そのままは移植できない。向こうの`src/validation.py`のfold構造に合わせて作り直す必要あり）
- 駅データ統合のコード一式（結果自体は「効果なし」で一致しているので、結果だけ共有すれば十分、コードの移植は不要）
- データ品質チェック（地区名の表記ゆれ`緑ケ丘`/`緑ヶ丘`等）→ チーム側の前処理にも同じ問題が無いか要確認

## チーム側にあって、自分側にまだ無いもの

- `cat_smooth=50`の調整（CV 0.20674→0.20360、LBでも同じ方向に改善を確認済み） — **自分のパイパラにも未検証、すぐ試す価値あり**
- ruff・型ヒント・docstring等のコード品質基盤
- Issue/PRベースの実験管理の仕組み（`docs/experiment-guide.md`、不採用も記録する文化）

## マージ後に確認したいこと（open questions）

1. `cat_smooth=50`を自分のtarget encoding併用パイプラインに入れても同じだけ効くか（target encodingと役割が一部重複する可能性があり、効果が減る/増えるかは未知数）
2. isotonic較正を`cat_smooth`調整済みのモデルに適用したら、単純な足し算（0.20360からさらに改善）になるか
3. 自分の`num_boost_round=2000`上限が実際に学習を制約していないか（best_iteration=1905は上限の95%、余裕を持たせて再検証すべき）
4. 間取り等の分解は、`cat_smooth`で生カテゴリの過学習が抑えられた後でも依然として効くか（分解の価値が`cat_smooth`と重複している可能性）
