# 検証方法

このコンペで使う検証方法（CV）と、それを選んだ理由をまとめる。実装は `src/validation.py`。

検証方法を変えたら、このファイルも更新する。

## 1. 検証で測りたいこと

検証の役割は、精度を直接上げることではなく、**どの変更が本当に効いたかを正しく判定すること**。物差しが狂っていると、効かない特徴量を採用したり、効く変更を捨てたりして、最終スコアが下がる。

このコンペの test には、次の 2 つの性質がある。検証もこれに合わせる。

- **test は学習データの直後の未来**：学習は 2019Q1〜2025Q2、test は 2025Q3〜2026Q1（1〜3 四半期先）
- **価格は上がり続けている**：test では、学習期間より高い価格水準を予測する必要がある

## 2. ウォークフォワード法

**過去のデータで学習し、その直後の期間を予測して答え合わせする**、という手順を、時点を少しずつ未来へずらしながら繰り返す方法。本番の「今あるデータで、まだ見ていない未来を当てる」状況を、過去の時点で何度も再現する。

```
時間 →   ■ = 学習   □ = 検証   · = 使わない

1 回目   ■■■■■■■■□□□·········
2 回目   ■■■■■■■■■■■□□□······
3 回目   ■■■■■■■■■■■■■■□□□···
                       ↑ 時点を前へ進める（walk forward）
```

### ランダム分割を使わない理由

ランダム分割では、2025 年のデータで学習して 2023 年を予測する、ということが起きる。価格が上がり続けているので、モデルは「この時期はこのくらいの価格」という相場を、検証期間の前後のデータから覚えてしまう。そのため検証スコアは良く出るが、本番では前後のデータがない未来を当てるので、スコアが落ちる。

ウォークフォワード法では、検証期間より後のデータを学習に一切使わない。本番と同じ情報の制約の下でスコアを測れる。

### 決めるパラメータ

| パラメータ | 意味 |
|---|---|
| 学習窓の形 | expanding：学習の始まりを固定し、どんどん長くする<br>sliding：学習の長さを固定し、窓ごと前へずらす |
| 検証期間の長さ（horizon） | 何期先まで予測するか。本番の予測期間に合わせる |
| ずらし幅（step） | 次の回へ何期進めるか |
| 回数（fold 数） | 何回答え合わせするか |
| 空白（gap） | 学習と検証の間を空けるか |

### expanding と sliding

```
expanding                sliding
■■■■■■□□□                ·■■■■■□□□
■■■■■■■■■□□□             ····■■■■■□□□
■■■■■■■■■■■■□□□          ·······■■■■■□□□
学習がどんどん長くなる      学習の長さは一定
```

- **expanding**：使えるデータを全部使う。データが多いほど強いモデル（決定木など）と相性がよく、出発点として標準的
- **sliding**：古いデータを捨てる。昔と今で価格の決まり方が違う場合に向いている

どちらがよいかは「古いデータが役に立つか」次第。

### 弱点

- **古い fold ほど学習データが少ない**：本番（全期間で学習）との条件の差は、古い fold ほど大きい
- **最初の方の期間は検証に使えない**：常に学習側になるので、その期間の予測精度は測れない
- **相場の変わり目に弱い**：検証期間の相場が、本番の期間と違う動きをしていると、CV と LB がずれる

## 3. 現在の設定（v1・暫定）

| パラメータ | v1 | 理由 |
|---|---|---|
| 学習窓の形 | expanding（いつも 2019Q1 から） | 出発点として標準的。古いデータが役に立つかは、実験で確かめる |
| 検証期間の長さ | 3 四半期 | test が 3 四半期なので |
| ずらし幅 | 3 四半期 | 検証期間どうしを重ねない |
| 回数 | 3 fold | 直近 9 四半期を検証に使う |
| 空白 | なし | test は学習の直後なので |

```
          2019 ─────────────── 2023 ───── 2024 ───── 2025Q2 │ test
fold 2    ■■■■■■■■■■■■■■■■■■ □□□                         │
fold 1    ■■■■■■■■■■■■■■■■■■■■■■ □□□                     │
fold 0    ■■■■■■■■■■■■■■■■■■■■■■■■■■ □□□                 │ ■■■ ← 本番
```

| fold | 学習 | 検証 | RMSLE（ベースライン） |
|---|---|---|---|
| 0 | 2019Q1〜2024Q3 | 2024Q4〜2025Q2 | 0.21431 |
| 1 | 2019Q1〜2023Q4 | 2024Q1〜2024Q3 | 0.20330 |
| 2 | 2019Q1〜2023Q1 | 2023Q2〜2023Q4 | 0.20261 |

- **CV スコア** = 3 fold の RMSLE の平均（ベースラインは 0.20674）
- **本番用のモデル**は、直近までの全データで学習し直す。test に一番近い時期のデータを捨てないため。木の本数は 3 fold の best_iteration の平均を使う
- 直近の fold 0 がいちばん悪い。時間トレンドの影響かもしれない（未確認）

## 4. 使わない手法と理由

| 手法 | 使わない理由 |
|---|---|
| ランダム KFold | 未来のデータで過去を予測することになり、CV が実際より良く出る（2 章） |
| 1 回だけのホールドアウト | test と条件は近いが、1 期間だけなので「たまたまその期間が当てやすかった」影響を受けやすい |
| 地域などで分ける GroupKFold | test は同じ地域の未来の取引なので、test の条件と合わない |
| Purged K-fold / CPCV（Bagged・Adaptive を含む） | 下記 |

**Purged K-fold / CPCV** は、主に金融データのために提案された手法で、金融特有の 2 つの問題を解くためのもの。

1. **ラベルが期間をまたぐ**：たとえば「t 日から 5 日後までのリターン」のように、1 つのラベルが将来の期間に依存する。学習と検証のラベル期間が重なってリークするので、重なる学習サンプルを取り除く（purge）。境目の前後を空けるのが embargo
2. **バックテストの過学習**：取引戦略を何度も試して選ぶと、たまたま良かった戦略を選んでしまう。CPCV は、学習と検証の組み合わせを総当たりして多数の検証パスを作り、スコアの分布で評価する

このコンペには、どちらの問題もない。

- 1 件の取引に 1 つの価格なので、ラベルは期間をまたがない。purge で取り除く対象がない
- test は学習の直後の期間なので、embargo で空白を入れると、かえって test の条件から離れる
- K-fold 系は検証期間より後のデータも学習に使う。このコンペで一番難しいのは未来の価格水準の予測なので、その難しさを CV が隠してしまう
- 検証データは 1 fold で約 3 万件あり、誤差は件数で平均されるので、多数の検証パスを作るほどのばらつきはない

## 5. 見直しの方針

v1 は暫定。良い CV かどうかは、**CV と LB が連動するか**（CV が良くなった変更で LB も良くなるか）で判断する。CV のスコアが良く見える切り方を選ぶのではない。

- 提出のたびに、実験記録の .json の `lb_public` に LB を書く。`uv run python -m src.summary` で CV と LB を並べて見られる
- 数回提出して、CV と LB がずれるようなら、fold の切り方をチームで見直す
- 見直すなら早めに行う。バージョンを変えるたびに、過去の実験と比べられなくなる

見直すときの候補：

- 1 四半期ずつずらして fold を増やす（ばらつきが問題になったら）
- 直近の fold を重く見る
- sliding window にする

「古いデータを捨てると良くなるか」のような学習データの選び方は、検証方法ではなくモデル側の変更。検証方法を固定したうえで、実験として試す。

### 変えるときの手順

1. チームで合意する
2. `src/validation.py` を変え、`VERSION` を上げる（v1 → v2）
3. このファイルの 3 章を更新する
4. `experiments/baseline.py` を実行し直して、新しいバージョンでの基準スコアを記録する
