## コンペの全体像と工程

東京都の中古マンション等の取引価格（総額）を予測する。評価指標は RMSLE（価格の比率のずれを測る指標）。学習データは 2019年第1四半期〜2025年第2四半期、テストは 2025年第3四半期〜2026年第1四半期で、テストは学習データより未来の期間になる。

学習から提出までを、次の工程に分けて考える（`docs/workflow.md`）。どの工程の変更も、同じ CV で良し悪しを判定する。

| 工程 | 中身 | ファイル |
|---|---|---|
| 0. EDA | データを眺めて理解する | `notebooks/` |
| 1. 前処理 | 文字列を数値にする（「30分～60分」「戦前」など） | `src/data/preprocess.py` |
| 2. 特徴量 | 新しい列を作る | `src/features/` |
| 3. 学習データの選択 | どの行を、どの重みで学習に使うか | `src/data/selection.py` |
| 4. 目的変数 | 何を予測させるか（今は log1p(価格)） | `src/model/target.py` |
| 5. モデル | LightGBM など | `src/model/lgbm.py` |
| 6. パラメータ | ハイパーパラメータ | `src/model/params.py` |
| 7. アンサンブル | 複数のモデルの予測を混ぜる | `src/model/ensemble.py` |
| 8. 後処理 | 予測値の補正 | `src/model/postprocess.py` |

## CV を固定する理由、Optuna を後回しにする理由

### CV（検証）

- ウォークフォワード法：過去で学習して、その直後の3四半期を当てる。これを3回（検証期間 2024Q4〜2025Q2、2024Q1〜2024Q3、2023Q2〜2023Q4）行い、平均を CV とする
- ランダム分割（KFold など）は使わない。2025年のデータで学習して2023年を当てることが起き、相場が上がり続けているので検証スコアだけ良く出て、本番で落ちる
- CV は「良くなったか」を測る物差し。人や実験ごとに違うとスコアを比べられないので、`src/validation.py` は全員共通で、合意なしに変えない
- 実験は「main の CV → 自分の変更の CV」で比べ、一度に変えるのは1つだけ

### ハイパーパラメータの探索（Optuna など）

- 最適なパラメータは特徴量や目的変数で変わる。今探しても、特徴量を足すたびに探し直しになる
- 3 fold の CV で何十回も探すと、たまたま CV に合った値を選んでしまう
- 実験のたびに探すと、CV の差が特徴量の効果なのかパラメータの効果なのか分からなくなる
- そのため #13 で理由のあるパラメータだけ一度見直して固定した。Optuna での探索は、特徴量が落ち着いてから最後に1回行う。仕組みは先に作っておいてよい

### scikit-learn の Pipeline について

`notebooks/baseline.ipynb`（最初のテンプレート）では、scikit-learn の `Pipeline` で前処理とモデルをつないでいた。`Pipeline` を使う一番の利点は、CV の fold ごとに、前処理（欠損の埋め方やカテゴリの番号付けなど）を学習データだけで `fit` できること。検証データの情報が前処理に漏れない（リークしない）。

この考え方は、藤瀬の PR の構成でも引き継いでいる。`main.py` の `train_and_predict()` を fold ごとに呼ぶので、学習データの選択・目的変数・学習・後処理は、その fold の学習データだけで動く。

一方で、`Pipeline` のクラスそのものは使っていない。このコンペで大事な次の処理が、`Pipeline` に乗せにくいため。

| 処理 | `Pipeline` に乗せにくい理由 |
|---|---|
| early stopping（LightGBM が検証データを見て木の本数を決める） | fold ごとに検証データをモデルへ渡す必要がある |
| 目的変数の変換（log1p、#7 の相場を引いて足し戻す処理） | `Pipeline` は特徴量（X）の変換が中心で、目的変数（y）を fold ごとに変換して戻すには別の仕組みが要る |
| 後処理（isotonic 較正など） | 学習データの中に内側の検証期間を作る処理を、1つの段に収めにくい |
| LightGBM のカテゴリ変数 | pandas のカテゴリ型をそのまま使っていて、scikit-learn の変換を通すと型が変わることがある |

あわせて、検証の分け方はランダムな KFold ではなく、時系列 CV（上の「CV（検証）」）にしている。

### 提出のルール（Kaggle の提出は1日1回まで）

- 提出できるのは、締め切りまでで残り10回ほど。1回をチームで分け合うので、誰が何を出すかを決めておく
- 個人の実験の良し悪しは、LB ではなく CV で決める。LB で選ぼうとすると、提出の枠が足りない
- 提出するのは main だけ。main が新しくなった日に、その日の担当が提出して、PR の本文に LB を書く（CV と LB が連動しているかの記録になる）
- 最終提出の候補は、締め切りの前の日までに提出しておく。締め切り当日の1回は、予備として残す
- Kaggle の1日の区切りは日本時間の朝9時。締め切りの 10/21（水）23:59 までに使えるのは、10/21 の朝9時から締め切りまでの1回が最後

## git の操作の流れ

### 用語

| 用語 | 意味 |
|---|---|
| リポジトリ | プロジェクトのファイルと、変更の履歴をまとめたもの。GitHub 上にあるもの（リモート）と、自分の PC にあるもの（ローカル）がある |
| main | 全員の共通の土台になるブランチ。ここに入ったものが「今のベスト」 |
| ブランチ | main から分かれた作業用の枝。実験 1 つにつきブランチ 1 本 |
| コミット | 変更をひとまとまりで履歴に記録すること |
| push | 自分の PC のコミットを、GitHub に送ること |
| pull | GitHub の最新を、自分の PC に取り込むこと |
| PR（プルリクエスト） | 「自分のブランチの変更を main に入れてほしい」という依頼。CV の結果を書いて、ほかの人に見てもらう |
| マージ | PR の変更を main に取り込むこと |

### Issue の作り方

Issue は「これからやること」の置き場所。実験を始める前に、必ず Issue を 1 つ作る（すでにあれば、それを使う）。

1. GitHub のリポジトリの「Issues」タブを開き、同じ内容の Issue がすでにないかを確かめる
2. 「New issue」を押して、テンプレートを選ぶ
   - **実験・タスク**：精度改善のために試したいこと、やるべきこと（ほとんどはこちら）
   - **不具合・困りごと**：動かない、エラーが出る、手順が分からない
3. テンプレートの欄を埋める（実験・タスクの場合）

   | 欄 | 書くこと | 例 |
   |---|---|---|
   | タイトル | `[実験] ` の後に、何をするかを 1 行で | `[実験] 間取りを部屋数と L・D・K の有無に分解する` |
   | 工程 | どの工程を変えるか（0〜8 から選ぶ） | 2. 特徴量 |
   | やること | 何を試すか、どのファイルを直すか | `src/features/` に間取りを分解する関数を足す |
   | なぜ効くと思うか | 仮説や根拠。EDA で気づいたことなど | 間取りは 48 種類あり、件数の少ない間取りを似た型とまとめられる |
   | 終わりの条件 | 何ができたら閉じるか | CV を main と比べ、採用・不採用を判断して PR を出す |

4. 右側の「Assignees」で、担当者（自分）を選ぶ。ラベル（`実験` など）はテンプレートで自動で付く
5. 「Create」を押す。Issue に番号（`#14` など）が付くので、ブランチ名や PR で使う

決めごと：

- Issue 1 つにつき、変更は 1 つ。2 つ試したいなら Issue を 2 つ作る
- 自分がやらない案でも、思いついたら Issue にしてよい（担当者は空欄のまま）
- 調べて分かったことや途中経過は、Issue にコメントで書き足す
- テンプレートは #3 で入るので、マージの後から使える

### 実験 1 つの流れ（`docs/experiment-guide.md`）

1. GitHub で担当の Issue を開き、右側の「Assignees」で自分を割り当てる
2. main を最新にして、実験用のブランチを作る

   ```bash
   git switch main
   git pull
   git switch -c feat/<テーマ>      # 例: feat/district-name
   ```

3. `src/` の 1 か所を直して、CV を確認する（main の CV と比べる）

   ```bash
   uv run python main.py
   ```

4. コードを整形してチェックする

   ```bash
   uv run ruff format .
   uv run ruff check --fix .
   ```

5. 変更を確認して、コミットして、GitHub に送る

   ```bash
   git status                       # 何が変わったかを見る
   git diff                         # 変更の中身を見る
   git add src/features/district.py # 直したファイルだけを指定する（git add . は使わない）
   git commit -m "feat: 地区名を市区町村名とつなぐ"
   git push -u origin feat/<テーマ>  # 2 回目からは git push だけでよい
   ```

6. GitHub で PR を作る
   - push すると、GitHub のリポジトリのページに「Compare & pull request」のボタンが出るので押す
   - 本文のテンプレートに、「main の CV → この PR の CV」の表を埋める
   - 本文に `Closes #<Issue 番号>` と書くと、マージしたときに Issue も閉じる
   - 作業の途中なら「Create draft pull request」を選ぶ（下書きの PR。ほかの人から見える）
7. CV が良くなったらレビューしてもらってマージ。良くならなかったら、結果を書いて `不採用` ラベルを付けて閉じる

### ほかの人の PR がマージされたら

main が新しくなるので、自分のブランチに取り込んで、CV を比べ直す。

```bash
git switch main
git pull
git switch feat/<テーマ>
git merge main
uv run python main.py            # 新しい main の上で CV を比べ直す
```

`git merge main` で「CONFLICT」と出たら、同じファイルの同じ場所をほかの人も変えている。分からなければ、無理に進めずにチームに聞く。

### よく使うコマンド

| コマンド | 意味 |
|---|---|
| `git status` | 今どのブランチにいて、何が変わっているか |
| `git branch` | 自分の PC にあるブランチの一覧（`*` が今いるブランチ） |
| `git log --oneline -5` | 最近のコミット 5 つ |
| `git switch <ブランチ名>` | ブランチを切り替える（変更をコミットしてからにする） |
| `git restore <ファイル>` | まだコミットしていない変更を取り消す（元に戻せないので注意） |

### やってはいけないこと

- main に直接コミット・push しない（必ずブランチを作って PR を出す）
- 他の人のノートブックを編集しない
- `git push --force` を使わない
- テスト期間（2025年第3四半期以降）の取引データを、外部から見たり取ったりしない

## Claude Code・Codex の導入

どちらもターミナルで動く AI のコーディングエージェント。リポジトリのファイルを読んで、コードを書いたり、コマンドを実行したりできる。チャットの AI と違い、リポジトリの中身とルールを前提に作業できる。

- Claude Code は `CLAUDE.md`、Codex は `AGENTS.md` を自動で読み込む。このリポジトリでは、`CLAUDE.md` が `AGENTS.md` を読み込むようにしてあるので、どちらを使っても同じルール（禁止事項、実験の手順、コードの書き方）が伝わる
- どちらか1つでよい。Claude Code は Claude の Pro 以上、Codex は ChatGPT の Plus 以上の有料プランが必要
- インストール：[Claude Code](https://code.claude.com/docs/en/setup)、[Codex](https://github.com/openai/codex)
- 必ずリポジトリのフォルダ（`condominium-resale-price-pred/`）で起動する。ほかのフォルダで起動すると、`AGENTS.md` や `CLAUDE.md` が読み込まれない

### 使い方の例

- 「Issue #8 をやりたい。どのファイルをどう直せばいいか教えて」
- 「`uv run python main.py` を実行して、main の CV と比べて」
- 「EDA で〇〇に気づいた。実験・タスクのテンプレートで Issue を作って」

Issue や PR はチーム全員が読むので、内容が合っているか、CV の数字が正しいかは自分の責任で確かめる。

- エージェントから Issue や PR を作るには、GitHub CLI（`gh`）のインストールとログイン（`gh auth login`）が必要
